# Project Foundation (PLUTO-01) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking — this plan is retrospective, documenting work already completed, so every step is checked off.

**Goal:** Stand up the TypeScript project scaffold, SQLite schema, env-var validation, shared domain types, and currency constants that every later Pluto AI module (bot, expense engine, budget, digest, webhook) builds on top of.

**Architecture:** A `src/config/` layer validates environment variables with Zod and exposes currency constants/conversion helpers. A `src/db/` layer wraps `better-sqlite3` with Drizzle ORM behind a lazily-initialized singleton that runs migrations on first access. A `src/types/` layer defines the domain vocabulary (`Transaction`, `Holding`, `Budget`, `Currency`, `Category`) that every other module imports rather than redefining. `src/utils/` provides a leveled logger and a thin currency-utility wrapper.

**Tech Stack:** TypeScript (strict, ES2020, commonjs), better-sqlite3, Drizzle ORM + drizzle-kit, Zod, dotenv, ESLint 10 (flat config) + Prettier, tsx (dev runner), node's built-in test runner (used starting with later modules).

**Spec:** [docs/superpowers/specs/2026-08-15-project-foundation-design.md](../specs/2026-08-15-project-foundation-design.md)

## Global Constraints

- All monetary amounts are stored as integer cents, never floats — every `amount`/`amount_sgd` column in the schema is `integer`.
- `Currency` is a fixed union (`SGD | MYR | USD | BTC | ETH | BETH`) and `Category` is a fixed 10-value union (`Food | Transport | Shopping | Entertainment | Bills | Health | Education | Travel | Groceries | Others`) — both live in `src/types/transaction.ts` as the single source of truth.
- `GOOGLE_API_KEY` must be a hard requirement in `env.ts` (no default, `min(1)`) — Pluto AI has no rule-based fallback for message understanding, so a missing key should fail startup, not degrade silently.
- `TELEGRAM_BOT_TOKEN` and `TELEGRAM_AUTHORIZED_CHAT_ID` stay optional in the env schema — their absence changes runtime behavior in later modules rather than failing startup here.
- The `db` singleton (`src/db/client.ts`) is the only place that owns Drizzle migrations; `npm run db:generate` / `npm run db:migrate` are the only supported ways to change the schema.

const envSchema = z.object({

### Task 3: Currency constants and conversion (`src/config/currencies.ts`, `src/config/exchange-rates.ts`)

**Files:** `src/config/currencies.ts`, `src/config/exchange-rates.ts`

**Interfaces:**
- Produces: `CURRENCIES`, `BASE_CURRENCY`, `DEFAULT_CARD_CURRENCY_MAP`, `EXCHANGE_RATES`, `convertCurrency()`, `toSGD()`, `formatCurrency()` (sync, static-rate); `getExchangeRates()`, `getExchangeRate()`, `refreshExchangeRates()` (async, cached, currently backed by the same static fallback table).

- [x] **Step 1: Define supported currencies and display metadata**

`CURRENCIES: Record<Currency, { symbol, name }>` for all 6 supported currencies (`SGD`, `MYR`, `USD`, `BTC`, `ETH`, `BETH`); `BASE_CURRENCY = 'SGD'`.

- [x] **Step 2: Define the card→currency map**

`DEFAULT_CARD_CURRENCY_MAP`: `OCBC`, `OCBC iPhone`, `DBS`, `UOB` → `SGD`; `Crypto.com`, `Binance`, `Gemini` → `USD`. (No `Maybank` entry — flagged as an open gap in PLUTO-03's acceptance criteria, not fixed here.)

- [x] **Step 3: Define static exchange rates and sync conversion helpers**

`EXCHANGE_RATES` (SGD = 1.0 baseline); `convertCurrency(amount, from, to)` converts via SGD as an intermediate; `toSGD(amount, currency)` is `convertCurrency(amount, currency, 'SGD')`; `formatCurrency(amount, currency)` renders `${symbol}${(amount/100).toFixed(2)}`.

- [x] **Step 4: Scaffold the async, cached exchange-rate service**

`src/config/exchange-rates.ts`: an in-memory `rateCache` with a 24-hour TTL, `getExchangeRates()` returns cached rates or calls `fetchExchangeRatesFromAPI()` (a placeholder that logs and returns the same fallback table — no real HTTP call yet), `getExchangeRate(from, to)` and `refreshExchangeRates()` built on top. Not wired into any call site yet — this is infrastructure for a future task.

- [x] **Step 5: Verify**

Run: `npx tsc --noEmit` — no type errors. Manual check: `toSGD(1000, 'MYR')` returns a sane cents value using the static rate.

### Task 4: Database schema and connection singleton

**Files:** `src/db/schema.ts`, `src/db/client.ts`, `src/db/index.ts`

**Interfaces:**
- Produces: `transactions`, `holdings`, `budgets`, `recurring_transactions`, `user_config` Drizzle tables; `getDb(): ReturnType<typeof drizzle>`, `db` (singleton).

- [x] **Step 1: Define the five core tables in `src/db/schema.ts`**

`transactions` (id, amount, currency, amount_sgd, merchant, category, source, card_name, note, created_at, updated_at), `holdings` (id, symbol, name, asset_class, quantity `real`, currency, market, cost_basis nullable, created_at, updated_at), `budgets` (id, category, amount, currency, amount_sgd, period, created_at, updated_at), `recurring_transactions` (id, amount, currency, merchant, category, day_of_month, is_active, created_at, updated_at), `user_config` (key PK, value). Timestamp columns default to `sql\`(unixepoch() * 1000)\``.

- [x] **Step 2: Write the connection singleton**

`initializeDatabase()`: ensure `./data` exists, open the SQLite file, `PRAGMA foreign_keys = ON`, wrap with `drizzle(sqliteDb, { schema })`. First implementation ran hand-written `CREATE TABLE IF NOT EXISTS` statements for all five tables directly inside `client.ts` (`initializeSchema()`), rather than generated migrations — this was replaced in Task 5 below.

`getDb()` lazily calls `initializeDatabase()` once; `export const db: any = getDb()` is evaluated at import time, so any module that does `import { db } from '../db'` triggers connection + schema setup as a side effect.

- [x] **Step 3: Verify**

Run: `npm run dev` — logs confirm the `./data/pluto.db` file is created and the five tables exist (checked via `sqlite3 data/pluto.db ".tables"` or `npm run db:studio` once drizzle-kit is wired in Task 5).

### Task 5: Migrate to drizzle-kit generated migrations and flat ESLint config

*(Later hardening pass — bundled with early budget-system scaffolding in the same commit, but foundation-owned since it changes how `src/db/client.ts` and the project's lint tooling work for every module.)*

**Files:** `src/db/client.ts`, `src/db/migrate.ts`, `src/db/migrations/*`, `drizzle.config.ts`, `eslint.config.mjs` (replaces `.eslintrc.js`), `package.json`

- [x] **Step 1: Add `drizzle.config.ts`**

```typescript
export default {
  schema: './src/db/schema.ts',
  out: './src/db/migrations',
  dialect: 'sqlite',
  dbCredentials: { url: process.env.DATABASE_URL || './data/pluto.db' },
} satisfies Config;
```

- [x] **Step 2: Generate the initial migration**

Run: `npm run db:generate` — produces `src/db/migrations/0000_wooden_doctor_octopus.sql` (the five `CREATE TABLE` statements from `schema.ts`) and `src/db/migrations/meta/0000_snapshot.json` + `_journal.json`.

- [x] **Step 3: Replace inline `CREATE TABLE IF NOT EXISTS` with `migrate()`**

`src/db/client.ts`'s `initializeDatabase()` now calls
`migrate(db, { migrationsFolder: path.join(__dirname, 'migrations') })`
instead of running hand-written SQL — the generated migrations and
`schema.ts` are now the single source of truth, and can no longer
silently drift apart.

- [x] **Step 4: Add the standalone migration runner**

`src/db/migrate.ts`: `runMigrations()` opens its own `better-sqlite3`
connection, runs `migrate()`, closes the connection, and logs
"Migrations completed successfully!". Exported for reuse (every test
file's `before()` hook imports and calls it against a scratch
`DATABASE_URL`), and also runnable directly via `npm run db:migrate`.

- [x] **Step 5: Replace `.eslintrc.js` with flat config**

The installed `eslint` was bumped to v10, which requires flat config.
`eslint.config.mjs`: `@eslint/js` recommended rules, `@typescript-eslint`
parser/plugin for `src/**/*.ts`, `no-unused-vars` as an error (with a
`^_` args-ignore pattern), `no-explicit-any` as a warning, ignoring
`dist/`, `node_modules/`, `data/`.

- [x] **Step 6: Verify**

Run: `npm run lint` (clean), `npx tsx -e "import('./src/db/migrate').then(m => m.runMigrations())"` (idempotent, safe against an existing dev db), `npm run dev` (boots and migrates automatically).
